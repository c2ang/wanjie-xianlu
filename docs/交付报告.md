## 4. 测试记录

```
node --test tests/core.test.mjs   → tests 18 / pass 18 / fail 0
node tools/validate_pack.mjs      → ✓ 校验通过（1396 篇 / 252 实体 / 318 关联）
node tools/smoke_import.mjs       → ✓ 导入链路与资料包一致
node tools/e2e_import.mjs         → ✓ 全链路通过（18 项断言）
node tools/check_ui.mjs           → ✓ UI 引用一致（27 个 id / 11 个动作）
```

开发过程中被测试抓出并修掉的实际缺陷（都是会让功能静默失效的那类）：

1. **JSON/JSONL 判定写错**：`/^\s*[[{]/` 只看首字符，JSONL 首字符也是 `{`，导致整包按单个 JSON 解析 → 导入 0 条。改为「先尝试整体解析，失败再逐行」，e2e 才通过。
2. **关联终点为空**：器灵→法宝的目标是法宝本体（不在四类实体里），原 schema 直接抛错，176 条关联会在导入时变成 invalid。现允许 `target_label` 作为库外对象，`related` 以「外部关联」返回。
3. **原文 id 撞车**：文档主键取正文哈希，6 组跨类目同内容的篇目拿到同一个 id。改为 `文件名|篇号|标题|正文` 联合哈希，重新生成后 id 唯一。
4. **warnings 未初始化**：`scope=auto` 补原文时 `payload.warnings.push` 抛 TypeError。格式化层补 `warnings: []`，面板警告区同时读 `payload.warnings` 与 `meta.warnings`。
5. **`node --test tests/` 在 Windows 上把目录当模块**，必须写全文件路径。

另有两处工程陷阱：Node 22 的 `cpSync(dir, existingDir, {recursive:true})` 在本机触发 0xC0000409 崩溃，安装脚本改为手写递归复制；`open().read()` 会做换行归一，校验类脚本必须用 `rb` 读再自行处理 `\r`。

## 5. 资料质量（如实交代）

- 原文 1396 篇，四类素材 252 条：女修 24 / 神佛 6 / 器灵 86 / 异兽 139。
- 质量：verified 31、inferred 7、pending 149、adapted 68。
- 这套资料是「设定百科」，不是人物名录，所以具名角色天然稀疏：
  - 女修 24 条几乎全是模板型（圣女型、魔女型、师姐型、女帝型…），适合当「人设骨架」而不是现成角色；
  - 异兽 139 条多是图鉴行（白虎族、凤凰、龙族…），适合抽取血脉/能力做设定；
  - 器灵 86 条：18 条来自原文行内条目（紫、青、造化有明确女性形态），68 条按下面的约定由法宝名生成；
  - 神佛 6 条（女娲、王母、观音等），字段较全但数量少。

### 5.1 器灵素材的处理方式（按你的要求改过）

你的要求是：**器灵只需要给一个法宝的名字，酒馆的模型会自行赋予女性特质**。所以资料包按这个约定处理：

- 从 04-资源物品 里认出 68 件具名法宝（诛仙剑、戮仙剑、陷仙剑、绝仙剑、盘古幡、六魂幡、混沌钟、太极图、山河社稷图、天地玄黄玲珑宝塔、定海珠、定风珠、芭蕉扇、打神鞭、照妖镜、阴阳镜、紫金铃、摄魂铃…），每件生成一条器灵素材，`name` 就是法宝名；
- 提取时排除混在 04 里的丹药与兽类（毒龙珠=毒丹、五色小圆珠=半成品丹、椒图=玄兽），避免把「丹」「兽」当器灵；
- 保留原文设定：`fields.artifact_name / artifact_type / grade` 与 `content` 里的「品阶 / 类别 / 形制 / 原文器灵注 / 使用限制」，例如诛仙剑会带上「原文器灵注：混沌凶兽饕餮残魂所化，嗜杀成性」；
- 不写死女性：`quality=adapted`、`adaptation_flag=true`、`gender_basis` 留空，工具返回里带 `material_note`——「素材只提供法宝名与形制；器灵的女性形态、样貌、性格由模型补全」；
- 可开关：设置里关掉「允许使用改编素材」后，这批素材整体排除，不会把模型补全当成资料库事实。

因此插件的另一半价值在**原文检索**：`/xianlu search scope=document keyword=器灵` 能直接拿到「器灵如何诞生、如何认主」的规则原文。这是把「素材稀疏」变成「设定可信」的关键设计。

设计取舍：
- 世界书触发词取「整名 + 按标点切出的片段」，长标题（如「资源物品｜经济体系细节设定（微观篇）」）也能靠「经济体系细节设定」命中；每条最多 6 个键。
- 角色卡只内嵌素材 + 01/02 两板块节选（406 条），1396 篇全塞进卡会拖慢导入、也超出常见 token 预算；要全文用插件或「设定原文」世界书。
- 世界书条目 `position=0`（角色设定之前）、`selective=true`、`order=100`，字段与酒馆自带世界书样例一致；`verify_share.mjs` 逐条比对齐全性。

## 7. 对接制卡器（v1.2.0 增补）

需求来源：制卡器要「按需取不等数量的素材」，需要一份可交付给第三方的调用规范。

- `docs/制卡器调用规范.md`：协议版本 `xianlu/1.2.0`，含四种接入方式（Function Tool / 斜杠命令 / 离线 CLI / 静态世界书）、5 个工具的参数表与边界、返回值字段表、三档详细程度预算、抽样与放宽语义、制卡流程与伪代码、素材→卡片字段映射、错误降级表、8 项自测清单。
- `docs/制卡器提示词.md`：三种接法各一段可直接粘贴的提示词。
- `schemas/`：由 `node tools/export_schemas.mjs` 从 `WJL_Tools.defs()` 直接导出（不手写，避免文档与代码脱节）：`xianlu-tools.openai.json`、`xianlu-tools.meta.json`、`xianlu-result.schema.json`、`xianlu-enums.json`。
- `tools/pick_random.py`：离线抽取 CLI，支持 `--combo female_cultivator:1,female_artifact_spirit:2`（一次取多类别不等数量）、`--seed` 复现、`--detail` 三档、`--names-only`、`--format md`。
- `tools/verify_cli_parity.mjs`：9 组参数 × CLI 与插件逐条比对 ID 序列，全绿；同时验证 `count=10` 上限。
- `xianlu_generate` 的 `count` 上限由 5 收到实测一致：schema `maximum` 与面板输入上限一并改为 10（实现里本来就是 clamp 1–10）。
- 数据修正：`gender_basis` 等字段原先会把整行表格（`| 经典形象 | 慈祥老者、温婉女修 |`）原样当证据句，改为 `basis_clean()/value_clean()` 转成「标签：内容」；重新生成资料包，数量不变（1396 / 252 / 318）。
